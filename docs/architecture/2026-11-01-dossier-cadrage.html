Une appli, deux générations, deux Terraform.

Le TD demande de construire une application web résiliente deux fois : une fois comme on l'aurait fait il y a 15 ans dans un datacenter d'entreprise (Platform 2), une fois comme une appli née dans le cloud (Platform 3). Le livrable, ce sont deux Terraform. La note se joue sur votre capacité à montrer, preuves à l'appui, ce qui change entre les deux.

Platform 2Redondance de l'infraVM nommées, SGBD installé dans une VM, stockage bloc, fichiers et batch de nuit, alerte puis humain. « Pets ».
Platform 3Résilience de l'applicationContainers jetables, services managés, objet, événements, multi-région, remédiation automatique. « Cattle ».

01

Ce que le projet est, concrètement

Le cours de Yannick Neff part d'une idée simple : « On ne fait pas de l'IT aujourd'hui comme il y a 20 ans ». À un instant T, une entreprise a plusieurs générations d'IT qui cohabitent. Le projet vous fait vivre cette cohabitation : même besoin métier, deux réponses d'époques différentes.

Trois glissements résument tout le cours (Cours 1, slide 8). Ce sont eux que votre soutenance doit rendre visibles :

Glissement 1

Infrastructure based → application based

En P2, c'est l'infra qui porte la qualité de service. En P3, c'est l'application qui est conçue pour survivre à une infra qui tombe.

Glissement 2

Redondance → résilience

P2 double les équipements (2 serveurs, 2 DC, réplique de base). P3 suppose que tout casse et se reconstruit tout seul.

Glissement 3

Pets → cattle

En P2, db-01 a un nom, on le soigne, on le patche. En P3, une instance malade est détruite et remplacée.

Le point clé à comprendre : vous faites les deux sur GCP. La Platform 2 n'est donc pas « l'ancien monde physique », c'est la colonne « Virtual 2 Virtual / DC as a Service » du cours (Cours 1, slide 10) : on utilise le cloud comme un datacenter virtuel, sans transformer l'application. Votre P2 émule un datacenter d'entreprise dans GCP. Votre P3 est la colonne « Born 2 be Cloud ».

Ce qui est demandé (écrit dans les slides)

  • Construire 1 application web résiliente en Platform 2 et en Platform 3
  • Livrable : 2 Terraform (un par plateforme)
  • ~3 suivis puis une soutenance

Ce qui n'est pas écrit et qu'il faut clarifier

  • GCP accepté (les exemples du cours sont tous AWS) ?
  • Appli imposée ou libre ? Démo live attendue ?
  • Grille de notation, dates des suivis, taille d'équipe

La liste complète des questions à poser est en bas, section Décisions.

Pièges côté P2

Ce qui ferait glisser votre P2 vers P3

  • Managed Instance Group avec autoscaling et autohealing : c'est la colonne « Cloud-Ready », plus du P2
  • Cloud SQL : un DBaaS est explicitement classé hors P2 dans le cours
  • Docker sur les VM : le container est la brique P3 du cours
  • Stocker les fichiers dans un bucket : l'objet est P3, P2 c'est bloc et NAS
Pièges côté P3

Ce qui trahirait une P3 « déguisée »

  • Une seule région, ou une base dans une seule zone
  • De l'état stocké dans l'instance (sessions, fichiers locaux)
  • Un cron de nuit au lieu d'événements
  • Des clics dans la console, ou des clés de service account dans le repo

Terraform des deux côtés, ce n'est pas contradictoire. Le livrable impose l'IaC partout. La différence est dans ce que le code décrit : en P2, Terraform construit un datacenter que des humains exploitent ensuite ; en P3, le code décrit l'application entière et son exploitation. Dites-le explicitement en soutenance, c'est exactement la nuance du cours entre « l'infra se builde » et « l'infra se code ».

03

L'application à construire

Le choix de l'appli compte : elle doit rendre visibles les différences P2/P3 (pic de charge, stockage de fichiers, traitement asynchrone, transaction). Une simple to-do list ne montrerait presque rien.

Recommandé

Billetterie d'événement

Ex. la billetterie du gala de l'école. Ouverture des ventes à 18 h 00 = pic de charge réaliste. Stock de places = transaction critique (pas de survente). Billet QR généré après achat = traitement asynchrone et fichier stocké.

Partage de photos avec traitement

Upload → miniatures. Très parlant pour bloc vs objet et batch vs événement. Moins bon pour montrer les transactions et la montée en charge.

Réservation de salles

Simple à coder, mais charge faible et peu d'asynchrone : la P3 paraîtra surdimensionnée et la démo sera plate.

Spec fonctionnelle minimale (billetterie)

  • Visiteur : liste des événements et places restantes
  • Acheter : décrément atomique du stock, jamais de survente
  • Recevoir son billet : QR code généré puis téléchargeable
  • Contrôle d'entrée : scan du QR, validation idempotente (un billet ne passe qu'une fois)
  • Admin : créer un événement, voir les ventes, exporter

API : GET /events, POST /events/{id}/orders, GET /tickets/{id}, POST /tickets/{id}/scan, GET /healthz. Pas de paiement réel.

Exigences non fonctionnelles (à afficher en soutenance)

CibleP2P3
Modèle SLA (Cours 1 sl. 9)Designed for failover, 99,9 %Designed for failure, always on
RTO perte d'une zone≤ 30 min (runbook)≤ 1 min (auto)
RPO≤ 5 min (réplication async)≈ 0 (multi-région synchrone)
Pic à l'ouvertureTenu jusqu'à la taille des VMAbsorbé par scale-out

Ce sont des cibles de départ, à confirmer par le protocole de test.

Le même parcours d'achat, vécu par chaque plateforme

P2 · data-driven
  1. nginx sur web-01 reçoit la requête
  2. app-01 ouvre une transaction SQL et décrémente le stock
  3. La commande attend en base
  4. Toutes les 15 min, le cron de batch-01 génère les QR et les dépose sur le partage NFS
  5. La nuit, un export CSV des ventes part vers le « partenaire » par fichier
P3 · event-driven
  1. Le load balancer global route vers la région la plus proche et saine
  2. api fait une transaction Firestore
  3. Il publie ticket.purchased sur Pub/Sub
  4. Le worker génère le QR dans Cloud Storage en quelques secondes
  5. Le même événement alimente BigQuery : stats de ventes en temps réel

C'est la slide « Data-driven vs Event-driven » (Cours 4, slide 6) rendue concrète : en P2 la source de vérité est la base, en P3 c'est le flux d'événements.

Un seul code, deux adaptateurs. Écrivez l'API avec une couche d'accès aux données interchangeable (Repository PostgreSQL ou Firestore, choisi par variable d'environnement). Vous gardez une seule base de code, et vous illustrez le facteur « services externes comme ressources attachées » mot pour mot. Stack conseillée : Python FastAPI ou Node, selon ce que l'équipe maîtrise.

06

Ce qui peut impressionner

Des pratiques actuelles, chacune reliée à une notion du cours pour rester dans le sujet. Classées de la plus rentable à la plus optionnelle.

Démo de chaos en direct

Impact fortEffort M

Pendant la soutenance, un tableau de bord montre P2 et P3 côte à côte sous charge k6. Vous « débranchez » une zone ou une région en direct. Le jury voit la courbe P2 tomber et la P3 rester verte.

Cours : test de DR, « allers-retours perpétuels » (Cours 4, slide 48). Prévoyez une vidéo de secours si le réseau de la salle lâche.

DRP testé en permanence

Impact fortEffort S

Un Cloud Scheduler casse une région chaque nuit et la rétablit, avec un historique des bascules. Littéralement « test de DRP permanent » du tableau du Cours 1.

SLO et error budget

Impact fortEffort S

Définir un SLO (99,9 % de requêtes en moins de 300 ms) dans Cloud Monitoring, avec alerte sur le taux de consommation du budget. C'est le vocabulaire SRE attendu en P3.

Coût affiché à chaque PR

Impact fortEffort S

Infracost commente chaque pull request avec le delta de coût mensuel, plus terraform plan et un scan de sécurité (Checkov ou Trivy). Montre P2 « toujours allumé » vs P3 à l'usage.

ITIL joué pour de vrai en P2

Impact moyenEffort S

Un template d'issue « Demande de changement » et un environnement GitHub protégé : l'apply P2 attend l'approbation d'un « CAB ». En P3, le déploiement part seul si les SLO sont bons. People / process / technologies en une image.

Traçage distribué

Impact moyenEffort M

OpenTelemetry dans l'API et le worker : une trace suit l'achat du load balancer jusqu'à Firestore puis Pub/Sub. Illustre « monitoring = détecter, observabilité = trouver la cause » (Cours 4, slide 31).

Canary avec rollback automatique

Impact moyenEffort M

La CI envoie 10 % du trafic à la nouvelle révision, observe le taux d'erreur 5 min, puis passe à 100 % ou revient en arrière. Démo : on pousse volontairement une version buggée.

Bonus « Platform 2.5 »

Impact moyenEffort L

Une variable Terraform qui fait passer la P2 en colonne « Cloud-Ready » du cours : MIG avec autohealing + Cloud SQL HA. Montre que vous avez compris les trois colonnes, et le chemin de migration réel d'une entreprise.

Supply chain sécurisée

Impact moyenEffort S

Image distroless, SBOM généré en CI, scan de vulnérabilités dans Artifact Registry. Renforce l'argument « rebuild plutôt que patch ».

Tableau de bord temps réel des ventes

Effet visuelEffort S

Abonnement Pub/Sub vers BigQuery puis Looker Studio : les ventes du test de charge apparaissent en direct. Rend l'architecture orientée événements tangible.

Budget GCP

Ordres de grandeur pour des machines de petite taille en Europe, à recalculer avec le simulateur GCP ou Infracost avant de lancer quoi que ce soit.

PosteP2, allumée 24/7P3, allumée 24/7
Compute~9 VM e2-micro / e2-small : 60 à 110 $/moisCloud Run : quasi nul hors tests (offre gratuite mensuelle)
Load balancer~20 $/mois~20 $/mois + Cloud Armor quelques $
DonnéesDisques et snapshots : ~10 $/moisFirestore, Pub/Sub, GCS : dans l'offre gratuite à faible trafic
Total indicatif~100 à 150 $/mois~30 à 50 $/mois

Pour rester à presque 0 €

  • terraform destroy de la P2 en fin de séance : la P2 coûte alors quelques dollars par jour d'usage
  • Alerte budget à 10, 25 et 50 $ dès le bootstrap
  • Labels platform=p2|p3 sur toutes les ressources

Crédits

  • Essai gratuit GCP pour un nouveau compte (historiquement 300 $ sur 90 jours, à vérifier au moment de l'inscription)
  • Crédits Google Cloud for Education : demande à faire par l'enseignant pour la classe

L'écart de coût est un argument en soi : la P2 paie sa redondance en permanence, la P3 paie à l'usage. Mettez la facture réelle dans le tableau de scores.
